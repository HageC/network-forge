# Architecture

The executable slice keeps a transport-independent deterministic simulator in `services/api/internal/sim` and exposes it through `services/api/cmd/api`. The Next.js client submits bounded models through server-side proxy routes; the browser does not compute authoritative metrics. `services/api/internal/store` persists projects, immutable architecture versions, normalized nodes and edges, workloads, run summaries and background jobs in PostgreSQL. The store records applied SQL migrations in `schema_migrations`. API processes claim queued or expired jobs with renewable leases, then run simulations, experiments, comparisons and saved-project runs independently of HTTP requests. Lease owners fence progress and completion writes; a saved-project run and its job result share one transaction. Stateless mode uses an in-memory job manager.

An architecture has stable node and edge IDs. Nodes declare kind, service time, concurrency, queue capacity and a synthetic hourly cost, plus gateway rate limit, cache hit probability, database connection limit, exclusive lock hold, bounded broker backlog, redelivery policy or queue-pressure scaling where relevant. Queue nodes acknowledge callers and dispatch separately counted background jobs. Directed edges declare latency, loss probability, bounded transport retries, an optional circuit breaker and a synthetic cost per million send attempts. A workload declares source, request rate, duration, seed and an optional application retry policy. The API is versioned under `/api/v1`; invalid input has a stable `error` field. The calibration endpoint evaluates aggregate measurements against bounded service-time scale candidates without mutating a saved project.

The engine uses integer microseconds and a monotonically increasing event sequence. Scheduled outages, partitions, node degradation and link loss spikes are events in the same queue as request processing. Keeping the engine independent of HTTP allows a later worker boundary without changing simulation results. Each saved run refers to the architecture version used, including its failure schedule. A submitted saved-project job captures the version at submission time. Run summaries omit trace payloads; sampled traces are stored separately and fetched with `GET /api/v1/projects/{id}/runs/{runId}/traces`. `POST /api/v1/experiments` runs bounded repeated-seed experiments; `POST /api/v1/comparisons` compares two model snapshots under common workload settings. Both are stateless and require no database. Synchronous endpoints remain available for existing API clients.

# Simulation model

The engine uses a virtual integer-microsecond clock. A min-heap orders events by `(time, sequence)`. A seeded PRNG governs packet loss and cache hits. Constant-rate arrivals generate bounded requests. Every node has finite concurrency and a FIFO queue. Full queues and lost packets fail requests. Sink completion records latency.

Ordinary nodes require at most one outgoing edge. A load balancer may have multiple outgoing edges; it chooses them in stable edge-ID round-robin order when its own processing completes. A gateway may reject arrivals exceeding its configured per-simulated-second rate limit. A cache requires exactly one origin edge. After cache processing, a hit completes the request at the cache and a miss travels to the origin. Hit rate is an independent seeded probability per request, not a key-distribution or TTL model. All nodes still use configured service time, concurrency and queue limits.

A database may set `connectionLimit`. Zero uses its configured concurrency; a positive value caps active operations at the smaller of concurrency and connection limit. Its FIFO queue absorbs excess arrivals up to `queueCapacity`. Connection utilization divides occupied slot time by the effective connection capacity; connection waits and rejections count pressure caused when the connection limit is below concurrency. Each operation holds a connection for the full service time. The model does not simulate query plans, replication or connection setup time.

A database may also set `transactionLockUs` up to its base service time. Each operation reserves a single exclusive lock for that many microseconds at service start. If the lock is already reserved, it waits while holding its connection, and completion moves back by the lock wait. `lockWaits` and `totalLockWaitUs` measure the resulting contention. This models one shared hot lock, not transaction isolation levels, deadlocks or multiple keys.

A `queue` requires exactly one outgoing edge to a worker path. It uses its own service time, concurrency and FIFO queue to process enqueue requests. When enqueue processing finishes, the caller completes and a separate background job is sent on the edge. Background completions, failures and timeouts are reported separately and do not change caller success or caller latency. A later queue on the same background path forwards that job without creating another. `worker` uses the ordinary finite service model.

Optional `brokerCapacity` limits outstanding background messages at a queue; a full broker rejects the caller before acknowledgment. `maxDeliveries` (0 defaults to one attempt, up to five) and `redeliveryDelayUs` schedule a fresh send from the queue's outgoing edge after a background failure. Exhaustion counts a dead letter. Backlog remains occupied until completion, terminal failure or run end. These are deterministic virtual broker semantics; messages are not stored outside the simulated run, and there is no visibility timeout, acknowledgment protocol or broker restart model.

Optional autoscaling starts at a node's configured concurrency. Queue pressure at or above `autoscaleQueueThreshold` schedules one additional slot after `autoscaleDelayUs`, up to `autoscaleMaxConcurrency`. A full-queue rejection also counts as pressure. If a queue remains above the threshold, subsequent slots require separate delay events. When `autoscaleIdleUs` is positive, an idle spare slot is removed after that delay, one slot per check, down to the base concurrency. A busy slot is never removed. Scaling events are deterministic and use the same virtual clock. Database connection limits still cap active database operations when more compute slots are added. Node utilization divides occupied-slot time by the time-integral of available slots; connection utilization uses the effective connection-capacity integral. `scaleUps`, `scaleDowns` and `peakConcurrency` describe the observed policy actions. Node scenario cost scales the configured base hourly rate in proportion to active slots over virtual time. This is a simple capacity policy, not CPU-based horizontal pod autoscaling; it has no instance startup resource model, hysteresis beyond configured delays, or provider billing increments.

Scheduled failures are part of the same event heap. A `node_outage` starts at `startUs` (inclusive), immediately fails active and queued work, and rejects new arrivals until `startUs + durationUs` (exclusive). Recovery allows later arrivals to process normally. An `edge_partition` blocks transmissions attempted while active; a request already in transit continues to its destination. Overlapping failures use reference counts, so the target recovers only after the last one ends. A `node_degradation` multiplies service time for operations starting during its window; overlapping multipliers compound, with service delay capped at 60 seconds. Active operations keep their original completion time. An `edge_loss_spike` adds an independent temporary loss probability to the edge's base probability for attempts made during its window; overlapping spikes compound their survival probabilities. Failure events at a timestamp are scheduled before initial request arrivals at that timestamp. `failureDrops`, `outageUs`, `edgeDrops`, `degradedOperations`, and `failuresTriggered` report modeled effects. Failure behavior is deterministic for a fixed seed.

Each edge may retry failed transmissions up to `maxRetries` (0–5), with exponential delays `retryBackoffUs * 2^attempt`. A retry reattempts the transport send; it does not reprocess the source node. Retries waiting at a source are failed if that source has an outage. Packet loss and partitions both increment `edgeDrops`. Optional circuit breakers open after a configured number of consecutive failed sends. While open, sends fail fast without consuming another packet-loss draw or scheduling a retry. A successful send resets the consecutive-failure count. `retries`, `circuitOpens`, and `circuitRejected` report the effects. This is a transport-level policy only; downstream application errors, response deadlines, half-open probes and fallback responses remain unmodeled.

The workload may also enable 1–3 application retries with a positive `applicationRetryBackoffUs`. When a caller attempt fails at a node or after transport retries are exhausted, the same logical request restarts from the workload source after exponential delay `backoff × 2^attemptIndex`. This reprocesses every node on its path and can add edge sends, cost and latency. `applicationRetries` counts scheduled restarts; `applicationRetryExhausted` counts callers that still fail after using their budget. A retry scheduled beyond the run horizon ends as a timeout. A caller already acknowledged by an asynchronous queue is complete, so its background job is not restarted by this policy. The original request ID and start time are retained for latency and sampled traces. There is no response path, idempotency-key model, duplicate side-effect model or per-error retry policy; treat recovery estimates as synthetic.

Generated = completed + failed + timed out at run end for caller requests. Background jobs have separate outcome counts. Percentiles use nearest-rank quantiles of observed completed caller-request latencies. Queue wait contributes to latency. Node utilization is occupied-slot time divided by available slot time during the modeled duration; it is not CPU utilization.

Queue metrics record one wait observation for each request that begins service: zero for immediate service and elapsed virtual time for work taken from the FIFO queue. Rejected requests have no wait observation. `queueRejected` counts full-queue rejections; mean and P95 queue wait use the same observed service starts.

The architecture review applies fixed rules to a completed run. It flags utilization at or above 85% together with queue delay or rejection, otherwise queue rejection alone; database connection rejections; gateway rate limiting; outage drops; background job failures; cache miss ratio at or above 70% with at least 10 cache decisions; failed send ratio at or above 5% with at least 10 attempts; and transport or application retries at or above 0.2 per generated request. Each finding cites measured values from the run and offers a scenario to compare. Scores are heuristic sorting weights, not probabilities or predicted benefit. `confidence: high` means the cited metric was directly observed by this simulator, not that the recommendation will improve production performance. Findings are saved with run history.

The engine deterministically samples up to 50 request indexes spread across the workload. Each sampled trace records virtual-time events for generation, node arrival, queueing, processing, transport attempts, retries, cache outcomes, failures and terminal status. Each trace retains at most 128 events; if the path exceeds that cap, the final retained event is replaced with the terminal outcome and `truncated` is set. Trace latency is end minus start for that request. Aggregate latency percentiles still use completed requests only. These are sequential lifecycle events, not nested distributed spans, because the current model has no response path or fork/join semantics.

Repeated-seed experiments execute the same model 2–100 times with seeds `baseSeed + runIndex`, subject to a 2,000,000 unit work estimate (`requests × nodes × repetitions × (1 + maxApplicationRetries)`). Each run reports actual completion throughput, error rate, and P95 latency from completed requests. A run with no completions counts as an SLO violation and is excluded from the mean P95 and its interval. The experiment reports sample standard deviation, empirical 5th–95th percentiles of run P95, and a deterministic 1,000-resample percentile bootstrap 95% interval for the mean run P95. This interval captures variation from seeded simulation randomness under fixed assumptions; it does not measure uncertainty in the architecture model or predict production traffic. Experiment requests use context cancellation; the event loop checks cancellation every 1,024 processed events.

Architecture comparison executes two repeated-seed experiments with the same request rate, duration, base seed, repetition count and P95 target. Source component IDs may differ across topologies. Failure schedules and component settings may differ intentionally. The objective is one of throughput, error rate or mean run P95 latency. The reported difference is candidate minus baseline over paired seed indexes. A deterministic 1,000-resample bootstrap interval over paired differences determines the winner only when its 95% bounds are entirely above or below zero in the beneficial direction. Otherwise the result is `inconclusive`; exact equality is `tie`. P95 comparison is `indeterminate` if either variant has a run with no completed requests, because completed-request latency is undefined for that run. Matching seeds provide reproducible pairing but not identical random events when different topologies consume random draws in different orders. The interval reflects simulator randomness under fixed assumptions, not model uncertainty.

The cost model uses a configured hourly rate for each node's base modeled capacity, charged through the simulated duration even during outages. Autoscaled slots multiply that base rate by the ratio of active to base slots over virtual time. A configured cost per million attempted edge sends adds transport cost. Edge attempts include successful transmissions, packet losses, partitions and retries; circuit-open rejections are not sends. `estimatedScenarioCost = sum(nodeHourlyCost × capacityTime / baseConcurrency / 3,600,000,000) + sum(edgeAttempts × edgeCostPerMillionAttempts / 1,000,000)`, where capacity time is measured in slot-microseconds. `estimatedHourlyCost` scales this scenario cost to an hour at the same load. Cost per successful request divides scenario cost by completed caller requests and is absent when none complete. Repeated-seed experiments aggregate scenario cost across runs and divide by total completions for their cost-per-success figure. The rates are synthetic user assumptions; the model does not price CPU usage, memory, storage, provider-specific transfer tiers or actual cloud invoices.

Limits: 100 nodes, 300 edges, 100 scheduled failures, 60 seconds, 10,000 caller requests, 250,000 events, 50 sampled caller traces with 128 retained events each, and 60 seconds per node service time or edge delay. Cycles are rejected. Fork/join, broker process persistence, per-error retry decisions, multi-key transaction contention, correlated failures and richer component-specific behavior remain unimplemented. Synthetic results are not production forecasts.

The HTTP job manager accepts simulation, experiment, comparison and saved-project-run work, with at most two jobs executing concurrently per API process and 32 recent jobs retained in memory. Progress counts terminal caller requests for a single simulation and completed runs for experiments and comparisons. Cancellation is cooperative through Go contexts. The workspace stores the active job ID locally so it can reconnect after a browser reload. With PostgreSQL, job input, status, progress and result are persisted. Workers claim queued or expired jobs with a 15-second lease, renew every five seconds, and fence progress and completion writes by lease owner. A restarted job recomputes from the beginning unless its result already committed. Saved-project runs commit their history row, sampled traces and successful job result in one transaction; replay returns the original run. In stateless mode, restarting the API loses jobs. The synchronous endpoints remain available.

Calibration compares observed throughput, error rate and P95 latency against the configured workload and evaluates nine shared service-time multipliers from 0.25 to 4. The score is a weighted sum of absolute relative errors (30% throughput, 30% error rate, 40% P95), with floors of 1 request/s, 1% error and 1 ms latency. It scales non-client node service and database lock times together. The selected scale is a scenario fit to one aggregate observation, not a per-node measurement or a validated production forecast. Check it against separate traffic samples before using it for planning.
